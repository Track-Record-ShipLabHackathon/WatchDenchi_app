# WatchDenchiの設計と実装順

Flutter（画面・フォーム・端末内状態）⇔ HTTP/JSON ⇔ Go（認証、検証、在庫、使用情報、残量の窓口）⇔ SQL ⇔ PostgreSQL（永続化）。
☆2ではGoからHTTP/JSONで独立したPython/FastAPIサービスを呼び、物理式の推定値を補正します。
FlutterはGoを接続先とし、GoがDBと推論の詳細を受け持ちます。Goの機能は一つのサービス内に置きます。必要になった段階でHTTPの処理、業務処理、SQLへのアクセスを分けます。

PostgreSQL 17.12を選んだのは、永続化とトランザクションをローカルとCIで同じDBで確認できるためです。
FastAPIを☆2のHTTP窓口に採用します。Python・FastAPI・モデル依存のバージョンは、モデルと互換性を確認して実装時に固定します。
開発中はDBだけComposeで動かし、Go・Flutterはホスト上で動かします。Flutterは既存のAndroid、iOS、デスクトップ、Webを含む試作を `apps/mobile` に取り込みました。試作の出典は `save/current-work` の `49e9af0ba13f4156af9777938c131a8b90cf9c5b` です。端末内の試作データとサーバーで管理する予定のデータには移行・接続の設計が必要です。

## 画面と遷移

| 移動 | 利用する画面 |
| --- | --- |
| ① / ② | ホーム画面 ↔ バッテリー画面 |
| ③ / ④ | バッテリー画面 ↔ バッテリー登録画面 |
| 分岐 | ホーム画面 → 機器画面（入力詳細は要確認） |
| ☆2 | ホーム画面 → コレクション一覧画面（詳細は要確認） |

FlutterのNAVIが遷移を担当します。APIへの保存と画面遷移は別処理です。保存成功後にどこに進むか、通信エラー時に何を残して再試行するかは画面担当と決めます。
ホーム画面は使用中の機器・乾電池・残量の目安と、在庫や機器入力への入口を持ちます。バッテリー画面は在庫の表示と使用電池の選択、バッテリー登録画面は種類・製造会社・本数・保管場所メモの入力を担当します。

## 端末側の保持と使用情報

- `access_token` は匿名認証用の値で、画面間とアプリ終了後も保持します。ホーム画面で自動取得を1回行う想定です。失効、端末の再インストール、安全な保持・再発行方法は要確認です。
- `draft_id` は初期値NULLで、画面間とアプリを終了するまで保持します。具体的なストレージ、終了後の復帰・破棄・完了時のリセットは要確認です。
- `draft_id == NULL` のとき `POST /api/device-battery` でDBに `draft` の行を作成し、返ったIDをFlutterが保持します。機器・電池はどちらから入力しても同じ行にPATCHで紐づけます。機器入力APIの詳細は要確認です。
- 画面間で保持する使用情報は `draft_id` のみです。バッテリー選択フラグは設けません。入力中のフォームは画面内で管理できます。機器IDと電池IDを端末に保持して両方そろってからPOSTする案は比較時の案です。

## データの現在地

| 設計上の名前 | PostgreSQLの対応と残っている項目 |
| --- | --- |
| CLIENT | `client`。整数の自動採番ID、資料の `datatime` に対応する `created_at timestamptz` |
| BATTERY | `battery`。整数の自動採番ID、資料の `registed_at` は `registered_at timestamptz`、種類・製造会社・保管場所は `text`、本数は0以上の整数、`client_id` はCLIENTへの外部キー。種類と製造会社は資料の候補のうち文字列を採用し、コード表が決まるまで試作の文字列入力と合わせる |
| DEVICE_BATTERY | 機器・電池・本数・使用開始時刻・status。将来のBATTERYへの外部キーに加え、機器と電池が未選択のdraftを許す制約と、クライアントへの帰属を設計する |
| DEVICE | 機器の項目・API・クライアントへの帰属を要確認 |

初回SQLは `client` と `battery` を作成します。トークンの永続化とDEVICE/DEVICE_BATTERYのスキーマは設計が決まった段階で追加します。
`status` は `draft`（作成時）・`active`（使用中）・`inactive`（使用終了）。`status != inactive` の一覧にはdraftも含まれます。

## 機能開発の順序

1. ☆1の匿名認証と端末単位のアクセス制御を決め、在庫登録・一覧までFlutterとGoで往復させる。
2. draftの作成・更新、どちらの入力順でも同じIDになる動作を確認。重複作成、放棄、activeへの条件、使用終了、在庫減算と重複登録、登録した在庫IDの返し方を決める。
3. 機器・電池・使用情報を表示。新品の乾電池を前提に、残量％の意味、測定・手入力できる値、物理式と誤差の扱いを決めて基準推定を実装。種類・本数以外に、機器の消費や現在使えるエネルギーなどが必要になる。
4. ☆2でPythonモデルの学習・評価に使えるデータとGoとの契約を決め、基準推定を補正する効果を検証。製造会社を活用する拡張やコレクション画面もこの段階で扱う。
